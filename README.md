# Lavanda API

Go 1.26+, PostgreSQL 16+. Конфигурация через окружение или `.env`, пример в `.env.example`.

```text
go run ./cmd/server migrate
go run ./cmd/server admin
go run ./cmd/server serve
go test ./...
```

Команда `admin` требует ADMIN_EMAIL и ADMIN_PASSWORD. Существующий аккаунт не перезаписывает.
Для смены забытого пароля укажите email существующего администратора в `ADMIN_EMAIL`,
новый пароль (от 8 символов) в `ADMIN_PASSWORD` и выполните `go run ./cmd/server admin-reset-password`.
Из родительской папки доступна команда `npm.cmd run admin:reset-password` (Windows).
Команда обновляет только существующего администратора, отзывает его сессии и ссылки восстановления.
После выполнения удалите `ADMIN_PASSWORD` из окружения или `.env`. Перезапуск API и миграции не нужны.
При создании карточки клиента обязательно только имя. Пустой email разрешён у нескольких клиентов;
заполненный email проверяется на корректность и уникальность. Для приглашения и регистрации нужен email.
Администратор может выбрать роль `client` или `master` и сохранить список `workplaceIds`
для мастера. Регистрация по приглашению сохраняет назначенную роль. Мастера не имеют доступа
к административным API. Мастер видит в /api/bookings только записи связанных рабочих мест; ему запрещено
создавать и отменять брони. Изменение роли зарегистрированного пользователя применяется к его аккаунту.
Роль администратора назначается только командой `admin`.
В production используйте Linux-бинарник и systemd; полная инструкция — `../README.md`.

API:

Рабочие дни мастера: `workDays` — массив дней недели (0 — воскресенье, 1 — понедельник,
… 6 — суббота), `reserveWorkdays` — закрепление всех связанных мест в эти дни с 09:00
до 21:00 по Москве. Для включения нужны дни и места. Новые брони в закреплённый день
запрещены, в том числе администратору; существующие записи не отменяются. Для снятия
блокировки измените настройки мастера. `/api/workplaces` возвращает `blockedWeekdays`,
а `/api/availability` учитывает закреплённые дни. Требуется миграция версии 6.

Приоритет администратора: если `POST /api/bookings` пересекается с действующими записями,
API возвращает 409 и `conflicts` для подтверждения, без изменений в БД.
Повторный запрос с `confirmedConflictIds` должен содержать точный текущий список конфликтов.
Сервер атомарно отменяет их целиком и создаёт новую запись; изменение списка требует нового
подтверждения. Обычным пользователям такая отмена недоступна.

`POST /api/bookings` принимает `workplaceIds` — список разных мест на один интервал
для одного клиента и необязательного мастера. Все записи создаются в одной транзакции;
ошибка любого места откатывает всю операцию. Ответ содержит массив `ids` и первый `id`
для совместимости. Старое поле `workplaceId` также поддерживается, но одновременно
передавать оба поля нельзя. Стоимость сохраняется отдельно для каждого места;
отмена каждой записи выполняется отдельно.

При создании записи администратор может передать `masterId`. Сервер проверяет роль мастера
и связь с выбранным местом. Назначенный мастер сохраняется в записи (`masterId`, `masterName`).
Мастер видит назначенные ему записи, а записи без назначения — по связанным рабочим местам.
После обновления необходима миграция версии 5 и перезапуск API.

Удаление доступно администратору: DELETE /api/admin/clients/{id} и DELETE /api/admin/workplaces/{id}.
Карточка скрывается, все связанные действующие записи отменяются, история сохраняется.
Для пользователя также отзываются сессии, приглашения и ссылки восстановления; вход блокируется.
Удалённое место нельзя повторно активировать через API. Администраторов удалять нельзя.
Ответ содержит cancelledCount. Пустой DELETE не требует Content-Type, но требует Origin и сессию.
После обновления выполните миграцию версии 7 и перезапустите backend.

- `GET /api/health`, `/api/workplaces`, `/api/availability?date=YYYY-MM-DD` — публичные данные.
- `POST /api/auth/login`, `/register`, `/forgot`, `/reset`, `/logout`; `GET /api/auth/me` — учётная запись.
- `GET/POST /api/bookings`, `POST /api/bookings/{id}/cancel` — собственные брони; администратор может передать clientId при создании.
- `GET/POST /api/admin/clients`, `PUT /api/admin/clients/{id}`, `POST /api/admin/clients/{id}/invite`.
- `GET/POST /api/admin/workplaces`, `PUT /api/admin/workplaces/{id}`.
- `GET /api/admin/bookings?date=YYYY-MM-DD` — все записи выбранного дня.

Приглашения: `GET /api/admin/clients/{id}/invite` открывает текущую ссылку,
`POST` на тот же адрес создаёт/обновляет её (старая аннулируется),
`POST /api/admin/clients/{id}/invite/send` отправляет текущую ссылку на email из карточки.
Отправка не продлевает срок и не меняет ссылку. Ответ об успехе означает приём письма SMTP-сервером.
Настройте `SMTP_HOST`, `SMTP_PORT` (обычно 587, STARTTLS), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`.
`PUBLIC_URL` должен быть адресом фронтенда, доступным получателю письма.

После обновления выполните `go run ./cmd/server migrate` и перезапустите API.
Миграция сохраняет существующие данные. Старые ссылки нельзя восстановить из хеша —
для них интерфейс предложит обновление. Новые токены приглашений хранятся в БД для
повторного открытия/отправки и доступны через API только администратору; после регистрации удаляются.

Изменяющие запросы: JSON и Origin, равный PUBLIC_URL. Авторизация — HttpOnly cookie. Цены в копейках, даты ISO 8601 с часовым поясом. Исключающее ограничение PostgreSQL блокирует пересечение активных броней одного места.

`TEST_DATABASE_URL` включает интеграционные тесты в уникальной временной схеме. Без неё они пропускаются. Не направляйте тесты на production.
